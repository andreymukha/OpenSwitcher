# Проект безопасного снижения задержки XTEST после H-06

**Дата:** 2026-07-29

**Статус:** проект решения подготовлен для проверки пользователем перед
планированием и реализацией

**Ветка эксперимента:** `perf/h06-xtest-latency`

**Базовый коммит:** `bcec535b3ebd8d09b3f8d737c41a51995401f045`

**Область:** только горячий путь XTEST executor-guardian в Cinnamon/X11;
подтверждение X11-мутаций и подготовка повторяющихся клавиш

## Краткий результат

H-06 устранил опасность оставленного synthetic key debt, но добавил к каждой
XTEST press/release две последовательные проверки X-сервера:

1. `xtest_fake_input(...).check()` уже ждёт серверное подтверждение запроса;
2. следующий `Synchronize` дополнительно выполняет
   `get_input_focus().reply()`.

Кроме того, перед одной коррекцией guardian повторно запрашивает одну и ту же
X11 keyboard mapping для каждого одинакового `Backspace`.

Предлагается убрать только эту доказуемо лишнюю работу:

- считать успешный `VoidCookie::check()` подтверждением конкретной XTEST
  мутации и передавать это подтверждение следующему протокольному
  `Synchronize`, не выполняя второй X11 round-trip;
- кэшировать результат проверки mapping только внутри одной ограниченной
  операции, сохраняя отдельный уникальный `PreparedToken` для каждого
  запланированного нажатия.

IPC-последовательность, ledger и все fail-stop правила остаются прежними.
Подобранные пользователем задержки также не меняются. Результат будет собран
отдельным DEB и сначала измерен в Linux Mint/Cinnamon/X11 ВМ. Ветка не
сливается автоматически: после замеров отдельно решается, оправдывает ли
выигрыш изменение.

## Причина отдельной работы

В сохранённой H-06 кампании измерялся интервал от первого `Backspace press` до
последнего replay `release`, а не полное время ручной коррекции:

| Показатель | До H-06 | H-06 |
|---|---:|---:|
| median участка Backspace/replay | 50,322 ms | 51,732 ms |
| p95 участка Backspace/replay | 53,247 ms | 54,432 ms |

После дополнительной проверки production input-debug полного F12-пути для
30 четырёхбуквенных слов:

| Показатель | До H-06 | H-06 |
|---|---:|---:|
| minimum | 112 ms | 117 ms |
| median | 122 ms | 128 ms |
| p95 | 126 ms | 137 ms |
| maximum | 127 ms | 137 ms |

Медиана полного пути выросла примерно на 6 ms, или на 4,9%. Это не означает,
что вся коррекция «занимает 50 ms»: прежняя формулировка относилась только к
части XTEST trace.

В той же конфигурации намеренно установлены:

- `backspace_ms = 10`;
- `typing_ms = 10`;
- `layout_delay_ms = 30`;
- фиксированное удержание каждого synthetic stroke около 2 ms.

Эти значения подбирались на практике для хрупкого X11-пути. Они не являются
целью оптимизации и не должны использоваться как запас времени, который можно
уменьшить ради красивого benchmark.

## Цели

1. Сократить полное время коррекции в Cinnamon/X11 без изменения видимого
   результата и без ослабления H-06.
2. Сохранить серверное подтверждение каждой отдельной XTEST press/release.
3. Сохранить принцип: key-up debt удаляется только после протокольного
   `SyncAck`.
4. Исключить повторные mapping round-trip для одинаковой клавиши в одном
   заранее подготовленном плане.
5. Сделать оптимизацию локальной для XTEST backend, чтобы добавление KDE,
   другого desktop или нового backend не требовало копировать её в общий
   synthetic-input слой.
6. Получить сопоставимые package-first измерения до решения о слиянии.

## Не входит в работу

- изменение `backspace_ms`, `typing_ms`, `layout_delay_ms` или 2 ms hold;
- изменение порядка, числа или значения synthetic key events;
- пакетное выполнение `PrepareKeys`/`ExecuteSegment`;
- новая версия guardian IPC;
- объединение нескольких press/release в один неподтверждённый сегмент;
- изменение ledger, emergency mirror или границ `Unreconciled`;
- изменение Wayland/uinput, clipboard, layout backend или логики коррекции;
- оптимизация аварийного пути ценой его доказуемости;
- автоматическое слияние результата только потому, что тесты прошли.

Полное batching может дать больший выигрыш, но меняет размер атомарного участка
и fault-модель. Оно намеренно отложено до результатов узкого варианта.

## Сохраняемые инварианты

### Инвариант 1. Каждая XTEST-мутация подтверждается X-сервером

Production `RustX11Connection::fake_key` не просто ставит запрос в локальный
буфер. Вызов `xtest_fake_input(...).check()`:

- отправляет XTEST request;
- при необходимости вставляет X11 sync request;
- flush-ит соединение;
- ждёт ответа сервера;
- возвращает ошибку запроса или транспорта.

Успешный `check()` означает, что сервер обработал предшествующую мутацию на
этом соединении. Удаляется не подтверждение, а второй следующий round-trip,
который повторно доказывает уже доказанный факт.

### Инвариант 2. Протокол и ledger не оптимизируются

Для каждого нажатия по-прежнему выполняются отдельные:

1. `PrepareKey`;
2. `ExecuteDown`;
3. `DownAck`;
4. `Synchronize`;
5. `SyncAck`;
6. `KeyUp`;
7. `UpAck`;
8. `Synchronize`;
9. `SyncAck`.

`Synchronize` остаётся явной границей протокола. Guardian только отвечает на
неё уже полученным серверным доказательством. Это сохраняет:

- один request in flight;
- уникальные sequence и operation ID;
- lost-ACK семантику;
- состояние `PossiblyDown`;
- удаление key-up debt только после `complete_synchronize`;
- terminal drain в обратном порядке;
- emergency cleanup при гибели daemon или guardian.

### Инвариант 3. Неизвестный результат остаётся долгом

Если `.check()` возвращает ошибку, локальное подтверждение не создаётся, даже
если транспортная ошибка теоретически могла произойти после применения
мутации. Guardian сохраняет консервативный debt и переходит к существующему
cleanup/fail-stop пути.

Повторный release в terminal cleanup допустим: успешный более поздний
`key-up.check()` подтверждает и этот release, и все предшествующие запросы на
том же X11 connection. Повторный key-up безопаснее ложного снятия долга.

### Инвариант 4. Mapping не переживает операцию

Кэш mapping:

- принадлежит одному `GuardianSession`;
- содержит текущий `OperationId`;
- очищается при первом `PrepareKey` нового operation;
- очищается при terminal transition;
- не переносится между session, server epoch или перезапусками guardian;
- ограничен существующим `MAX_PREPARED_TOKENS`;
- не меняет генерацию уникального `token_id`.

Все ключи операции подготавливаются до первой мутации. Кэш является явным
frozen preflight snapshot для этой bounded-операции. Текущие повторные чтения
mapping также не дают атомарного snapshot: mapping может измениться сразу после
любого из них. Поэтому запрет кэша между операциями важнее повторного чтения
одного и того же keycode несколько раз в одном плане.

## Компоненты решения

### 1. Типизированное подтверждение X11-мутации

В `src/daemon/xtest_guardian/x11.rs` внутренний
`X11ConnectionBoundary::fake_key` должен явно представлять контракт
«вернуть успех только после server check». Рекомендуемое имя —
`checked_fake_key`; успешный вызов возвращает закрытый тип подтверждения, а не
неразличимый `()`.

`GuardianX11Executor` хранит не более одного последнего подтверждения:

```text
checked key-down/key-up
  -> pending_confirmation = Some(proof)

protocol Synchronize
  -> consume pending_confirmation
  -> return success without get_input_focus round-trip
```

Если `Synchronize` вызван без успешной предшествующей мутации, executor
возвращает typed invariant error. Нельзя превращать отсутствие доказательства
в успешный `SyncAck`.

Новая успешная мутация может заменить ещё не потреблённое подтверждение только
на аварийном повторном release-пути. Её `.check()` подтверждает весь
предшествующий порядок того же X11 connection. Обычный протокол по-прежнему не
разрешает вторую мутацию до `Synchronize`.

`X11ConnectionBoundary::round_trip` сохраняется:

- для отдельного `EmergencyX11Releaser`;
- как явная граница для мест, где до round-trip нет checked mutation.

Аварийный releaser не является горячим пользовательским путём, поэтому его
явный дополнительный round-trip в этой работе не меняется.

### 2. Operation-scoped mapping cache

В `src/daemon/xtest_guardian/service.rs` `GuardianSession` хранит bounded
таблицу:

```text
OperationId -> [(evdev_code, x11_keycode, server_epoch)]
```

Обработка `PrepareKey`:

1. `ProtocolState::accept` сначала подтверждает допустимость request,
   operation и deadline.
2. Если operation отличается от cached operation, старый кэш очищается.
3. При первом `evdev_code` выполняется существующая полная
   `executor.prepare_key`.
4. Повторный `evdev_code` получает тот же проверенный keycode/epoch без нового
   X11 mapping round-trip.
5. В обоих случаях создаётся новый монотонный `PreparedToken`.
6. `ProtocolState::record_prepared` остаётся единственным владельцем
   подготовленного token и его состояния.

Для четырёх одинаковых Backspace mapping читается один раз, но ledger
по-прежнему видит четыре разных нажатия и четыре разных token.

Кэш не должен попадать в общий `SyntheticOperation`: это X11-специфичная
оптимизация, не являющаяся обязанностью будущих KDE/Wayland/uinput backend.

### Порядок внедрения

Две оптимизации реализуются независимыми коммитами:

1. сначала типизированное подтверждение и удаление второго round-trip;
2. затем operation-scoped mapping cache.

Для обеих точек собираются отдельные артефакты. Это позволяет измерить вклад
каждой оптимизации и полностью отбросить mapping cache, если первый этап уже
даёт достаточный выигрыш или второй не оправдывает дополнительное состояние.

## Ошибочные и прерванные пути

### Ошибка mapping

Первое неуспешное чтение не кэшируется. Операция завершается существующей
backend failure. Никакая XTEST-мутация к этому моменту ещё не начата.

### Ошибка `checked_fake_key`

Подтверждение не публикуется. `record_down_attempt` сохраняет возможный долг,
после чего выполняется существующий terminal cleanup. Для key-up долг не
снимается.

### Ошибка или отсутствие `Synchronize`

Без pending confirmation `SyncAck` запрещён. Если confirmation был локально
потреблён, но IPC ACK потерян, guardian protocol/emergency mirror остаются
авторитетными и выполняют повторный release по существующим правилам.

### EOF, SIGTERM и Drop

Terminal cleanup продолжает выполнять отдельный `key_up` для каждого
авторитетного debt. Каждый успешный cleanup key-up создаёт новое server
confirmation, которое потребляется cleanup `synchronize`. Deadline и итоговый
`Reconciled`/`Unreconciled` не меняются.

### Гибель daemon

Guardian остаётся владельцем server-side ledger и освобождает debt. Удаление
второго обычного round-trip не меняет lifetime или cgroup separation.

### Гибель guardian

Emergency connection использует заранее проверенные token и собственный
явный round-trip. Этот путь не оптимизируется.

## Тестовая стратегия

Реализация выполняется через TDD. Сначала добавляются падающие тесты, затем
минимальный код.

### Unit и protocol tests

Нужны проверки:

1. `checked_fake_key` создаёт proof только после успешного boundary call.
2. `GuardianX11Executor::synchronize` потребляет proof без вызова
   `round_trip`.
3. `synchronize` без proof возвращает invariant error.
4. Перед каждой новой mutation старый proof извлекается из pending state;
   ошибка новой mutation не может оставить доступным proof предыдущей.
5. Повторный cleanup key-up заменяет старый proof и успешно подтверждается.
6. Четыре одинаковых `PrepareKey` одной операции выполняют один mapping query,
   но возвращают четыре уникальных token.
7. Разные keycode одной операции валидируются отдельно.
8. Та же клавиша в следующей операции валидируется заново.
9. Mapping error не кэшируется.
10. Terminal transition очищает operation cache.
11. Lost down/up ACK, EOF и cleanup failure сохраняют прежние debt/proof
    результаты.

Существующие fault-matrix, process tests и protocol tests не ослабляются и не
заменяются более узкими тестами.

### Статические gates

Перед сборкой DEB:

- `cargo fmt --all -- --check`;
- `cargo test --locked --all-targets --features settings-ui
  -- --test-threads=1`;
- release build/package checks;
- diff exact XTEST event-plan tests;
- проверка отсутствия изменений delay/config/protocol constants.

### Package-first проверка в Linux Mint/Cinnamon/X11

Сравниваются три состояния:

1. сохранённый baseline до H-06;
2. точный H-06 DEB;
3. новый DEB из performance-ветки.

Для непосредственного решения используются повторно установленные H-06 и
performance DEB в одной и той же сохранённой ВМ, с одной конфигурацией и
одинаковым четырёхбуквенным сценарием.

Собираются:

- не менее трёх чередующихся серий по 30 успешных F12-коррекций для каждого
  сравниваемого состояния;
- full completion `elapsed_ms`;
- высокоточный интервал от первого Backspace press до последнего replay
  release;
- minimum, median, p95 и maximum;
- exact normalized press/release trace;
- guardian aggregate p50/p95/max;
- отсутствие timeout и unreconciled debt.

Производительность считается улучшенной только при устойчивом сдвиге
распределения, а не по одному лучшему запуску. Заранее не устанавливается
процент, который автоматически разрешает merge: пользователь отдельно
оценивает практическую ценность результата.

### Safety/runtime gates кандидата

Так как код касается доказательства release, перед рекомендацией к слиянию в
Mint повторяются:

- обычная четырёхбуквенная коррекция;
- shifted/caps/modifier сценарии из H-06;
- exact event count/order;
- daemon `SIGKILL` с восстановлением клавиатуры и чистым keymap;
- guardian `SIGKILL` с emergency release и чистым keymap;
- штатный stop/restart;
- отдельный probe, который видит применённую XTEST mutation после
  `checked_fake_key`, но до локального протокольного `Synchronize`;
- проверка логов на timeout, protocol failure и `Unreconciled`.

Ubuntu/GNOME/Wayland не использует изменённый горячий путь. Для него полный
performance-повтор не нужен. Если кандидат выбран для интеграции, перед
слиянием выполняются package install/upgrade/purge и функциональный smoke,
чтобы доказать отсутствие побочного влияния.

## Критерии решения после измерений

Кандидат может быть рекомендован к слиянию, только если одновременно:

1. exact synthetic event trace не изменился;
2. deliberate delays и пользовательская конфигурация не изменились;
3. все unit/process/fault tests проходят;
4. runtime crash gates подтверждают прежнее освобождение;
5. полная коррекция не стала медленнее;
6. выигрыш повторяется и заметно превышает шум;
7. diff остаётся узким и локальным для guardian X11.

Даже при выполнении этих условий merge выполняется только после отдельного
решения пользователя.

Если выигрыш мал или нестабилен, performance-ветка сохраняется как результат
эксперимента, а рабочий H-06 код остаётся без изменений. Следующим вариантом
не становится автоматическое batching: его необходимость обсуждается
отдельно.

## Архитектурная оценка

Решение соответствует приоритетам проекта:

- **надёжность:** ни одна server confirmation не удаляется, меняется только
  место её использования;
- **безопасность:** ledger, lost-ACK и emergency release остаются
  консервативными;
- **производительность:** убираются повторные X11 round-trip, а не защитные
  задержки пользователя;
- **расширяемость:** оптимизация закрыта внутри XTEST guardian и не создаёт
  обязанностей для нового desktop/backend;
- **проверяемость:** старый и новый пути сравниваются точными DEB в одной ВМ;
- **обратимость:** исходный H-06 commit и его артефакты не меняются.

Основной остаточный риск — реальная семантика и стоимость `.check()` зависят от
X11/x11rb и должны быть подтверждены runtime trace, а mapping snapshot может
устареть в крайне коротком окне операции. Кэш намеренно не переживает
operation, и текущее многократное чтение также не создаёт атомарной защиты от
смены mapping. Эти риски проверяются тестами и Mint runtime до любого решения
о слиянии.
