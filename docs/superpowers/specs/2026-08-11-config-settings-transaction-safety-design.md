# M-04 + M-05: атомарная конфигурация и безопасное обновление настроек

Дата: 2026-08-11
Статус: согласовано пользователем, готово к реализации

## Контекст

Аудит оставил две связанные проблемы:

- **M-04:** `AppConfig::save_to_path()` записывает `config.toml` напрямую через
  `fs::write`. Сбой, нехватка места или остановка процесса во время записи могут
  оставить обрезанный либо частично записанный файл.
- **M-05:** D-Bus `UpdateSettings` принимает полный `SettingsDto`. Окно настроек,
  открытое до изменения через tray или другой клиент, может позднее сохранить
  старые значения полей, которых пользователь в этом окне не менял.

Tray меняет только `auto_switch_enabled`. Пользователь выбрал простую продуктовую
семантику: для одного и того же параметра побеждает последняя применённая
операция, а несвязанные параметры не должны случайно перезаписывать друг друга.

## Цели

1. После любой прерванной записи читатель видит либо предыдущий, либо новый
   целый `config.toml`, но не промежуточное содержимое.
2. Окно настроек сохраняет только действительно изменённые поля.
3. Обновления разных полей объединяются; обновления одного поля применяются в
   порядке, установленном демоном.
4. Финальная конфигурация полностью валидируется до commit.
5. После неудачи диск, память демона и опубликованный input snapshot не должны
   расходиться.
6. Изменение не затрагивает обработку клавиатуры, коррекцию текста, раскладки,
   clipboard и подобранные задержки.

## Не входит в задачу

- revision/CAS, конфликты и диалоги ручного слияния;
- история версий, резервные копии и восстановление произвольно испорченного
  пользователем TOML;
- наблюдение за ручным редактированием `config.toml` во время работы демона;
- изменение отдельного lifecycle автозапуска через пользовательские сервисы;
- изменения input pipeline или опасные runtime fault-инъекции на хосте.

Ручное изменение файла по-прежнему гарантированно подхватывается после
перезапуска демона. Единственным владельцем конфигурации во время обычной работы
считается daemon.

## Выбранный подход

### 1. Patch изменённых полей

Вместо полного слепого снимка D-Bus принимает patch. Для простого и стабильного
D-Bus-контракта он содержит:

- маску изменённых полей;
- `SettingsDto` со значениями, из которого используются только отмеченные
  маской поля.

Поля маски соответствуют текущим полям `Settings`:

- `auto_switch_enabled`;
- `fix_two_capitals`;
- `fix_accidental_caps_lock`;
- `layout_delay_ms`;
- `manual_correction_hotkey`;
- `selected_text_hotkey`;
- `layout_switch` как одно неделимое поле.

Неизвестные биты отклоняются. Пустая маска является допустимым no-op: запись на
диск и публикация нового поколения не выполняются, но клиент получает актуальный
снимок. Это нужно, в частности, когда изменился только отдельный checkbox
автозапуска.

Значения полей без установленного бита полностью игнорируются и сами по себе не
могут вызвать ошибку валидации. Валидируется только итог после наложения
отмеченных полей на актуальное состояние.

Option-поля непосредственно в D-Bus DTO не используются: стандартный D-Bus не
имеет естественного `Option<T>`, а маска оставляет контракт типизированным и
не требует динамического словаря variant-значений.

### 2. Семантика last-write-wins по полю

Daemon под `settings_update_gate`:

1. читает последнюю конфигурацию из `ConfigService`;
2. накладывает только отмеченные patch-поля;
3. валидирует получившийся целый `Settings` и `AppConfig`;
4. атомарно сохраняет конфигурацию;
5. только после commit заменяет in-memory config и публикует runtime snapshot.

Операции, меняющие одно поле, упорядочиваются этим gate. Поздняя операция
побеждает только для своих отмеченных полей. «Последней применённой» считается
операция, чей commit выполнен позднее в этом последовательном порядке.

Примеры:

- tray выключил автопереключение, затем окно сохранило только
  `fix_two_capitals` — автопереключение остаётся выключенным;
- окно явно изменило `auto_switch_enabled` и сохранило после tray — значение из
  окна побеждает;
- два окна изменили разные параметры — сохраняются оба изменения;
- два окна изменили один параметр — побеждает последний завершившийся commit.

Если объединение полей создаёт невалидную комбинацию, например одинаковые
горячие клавиши, вся операция отклоняется до записи. Частичного применения нет.

### 3. Итоговый снимок в ответе

`UpdateSettingsResult` возвращает фактически committed `SettingsDto`, а не только
текст сообщения. Окно после успеха принимает этот снимок как новый `loaded` и
`draft`.

Это важно, когда между загрузкой окна и Save tray изменил
`auto_switch_enabled`: окно сразу показывает реальное итоговое состояние и не
остаётся со stale-копией.

При ошибке draft пользователя остаётся доступным для повторного сохранения.
Существующая последовательность применения checkbox автозапуска сохраняется:
сначала committed-настройки демона, затем операция с пользовательским сервисом.

## Атомарная запись `config.toml`

`AppConfig::save_to_path()` выполняет:

1. валидацию и TOML-сериализацию полностью в памяти;
2. создание родительского каталога;
3. создание приватного уникального временного файла в том же каталоге;
4. `write_all` всего содержимого;
5. `sync_all` временного файла;
6. атомарный `rename` поверх `config.toml`;
7. `sync_all` родительского каталога;
8. автоматическое удаление временного файла на любом пути до `rename`.

Для временного файла используется `tempfile::NamedTempFile`, уже присутствующий
в lockfile как dev dependency; он переносится в обычные dependencies. Временный
файл имеет mode `0600`. После rename итоговый файл также остаётся приватным и
принадлежит пользователю daemon.

Временный файл обязан находиться рядом с `config.toml`: только тогда rename не
пересекает файловые системы и остаётся атомарным. Если конечный путь является
symlink, rename заменяет сам symlink и не следует к неожиданной цели.

### Commit point и ошибки

Commit point — успешный `rename`.

- Ошибка валидации, сериализации, создания, записи, file sync или rename не
  меняет старый файл и не меняет in-memory config.
- После успешного rename откатывать файл назад нельзя: другой читатель уже мог
  увидеть новую версию. Поэтому daemon принимает новый config в память даже
  при редкой ошибке последующего directory sync и фиксирует предупреждение о
  неподтверждённой durability.
- Ошибка directory sync не выдаётся как «ничего не сохранено»: это создало бы
  расхождение между реально заменённым файлом и старым состоянием памяти.
- Успешный directory sync означает подтверждённый durable commit в доступной
  файловой системе.

Для различения этих случаев atomic helper возвращает компактный outcome:
`Durable` либо `CommittedDurabilityUncertain`. Ошибки до commit остаются обычным
`Err`. Это единственное дополнительное состояние; общий журнал транзакций или
многофайловый протокол не вводится. Production-caller фиксирует редкое
durability-предупреждение без содержимого настроек и без пути временного файла.

## Компоненты и границы

### `src/config.rs`

- атомарный same-directory replace;
- outcome commit/durability;
- сохранение прежней валидации и TOML-формата.

### `src/model.rs`

- типизированная маска полей и `SettingsPatchDto`;
- наложение patch на актуальный `Settings`;
- итоговый committed snapshot в `UpdateSettingsResult`.

### `src/daemon/runtime.rs`

- единая сериализация patch, tray toggle и runtime layout redetection через уже
  существующий `settings_update_gate`;
- persist до замены in-memory config;
- публикация input snapshot только после commit;
- отсутствие публикации для фактического no-op.

### `src/dbus/mod.rs`

- `GetSettings` остаётся чтением полного актуального снимка;
- `UpdateSettings` принимает patch вместо полного слепого DTO;
- изменение D-Bus-сигнатуры fail-safe для старого settings-процесса: старый
  вызов получает ошибку сигнатуры и ничего не записывает. После обновления DEB
  окно настроек следует закрыть и открыть заново.

### `src/settings_ui`

- `DomainState` строит маску сравнением `loaded` и `draft`;
- клиент отправляет patch;
- после успеха state принимает returned committed snapshot;
- после ошибки draft и доступность повторного Save сохраняются.

## Инварианты

1. Неотмеченное поле никогда не берётся из stale DTO при commit.
2. Полная валидация выполняется над результатом наложения patch.
3. До успешного rename память и runtime publication не меняются.
4. После успешного rename память соответствует новому файлу, независимо от
   результата directory sync.
5. `settings_update_gate` задаёт единый порядок patch, tray toggle и изменений
   layout settings внутри daemon.
6. `UpdateSettingsResult.settings` равен состоянию `ConfigService` после
   операции.
7. No-op не пишет файл и не увеличивает runtime generation.

## Проверки

### Unit: config

- создание нового файла и roundtrip;
- замена существующего файла даёт только полный новый TOML;
- итоговый mode `0600`;
- symlink конечного файла заменяется, его target не изменяется;
- ошибка до rename сохраняет исходный файл и не оставляет temp;
- тестовый parent-sync seam подтверждает outcome
  `CommittedDurabilityUncertain` после уже выполненного rename.

Небольшой seam ограничивается операцией directory sync; универсальная абстракция
файловой системы не создаётся.

### Unit: settings/runtime/UI

- patch меняет только отмеченные поля;
- неизвестная маска отклоняется, пустая — no-op;
- итоговая объединённая конфигурация валидируется целиком;
- tray и patch одного поля подчиняются last-write-wins;
- patch несвязанного поля не отменяет tray toggle;
- runtime layout redetection не затирается patch другого поля;
- UI строит правильную маску и принимает committed snapshot;
- ошибка сохранения сохраняет draft;
- autostart-only Save не вызывает запись config.

### D-Bus и package

- два D-Bus-клиента меняют разные поля без потерь;
- два D-Bus-клиента меняют одно поле: последний commit побеждает;
- `UpdateSettingsResult` совпадает с `GetSettings`, `IsEnabled` и TOML;
- invalid merged settings не меняют файл или runtime;
- полный Rust gate с `--features settings-ui`;
- package shell gates и сборка следующего канонического DEB;
- минимальный package-first smoke настроек в Mint/Cinnamon/X11 и
  Ubuntu/GNOME/Wayland без input fault injection;
- короткая пользовательская проверка DEB перед слиянием.

## Производительность и риск регрессии

Настройки сохраняются редко и вне input path. Дополнительные file/directory
`fsync` не влияют на набор текста или скорость коррекции. Patch уменьшает объём
логических изменений и использует уже существующий gate; новые фоновые потоки,
таймеры и polling не добавляются.

Обычные функции OpenSwitcher должны работать без изменений. Риск сосредоточен в
D-Bus/settings UI и package-upgrade совместимости, поэтому runtime-проверка
ограничивается этими границами, а дорогая полная input-кампания остаётся общей
финальной проверкой после закрытия оставшихся задач аудита.
