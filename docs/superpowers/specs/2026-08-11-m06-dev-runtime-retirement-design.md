# M-06: вывод прямого dev-runtime из эксплуатации

Дата: 2026-08-11
Статус: согласовано пользователем, готово к реализации

## Контекст

Аудит выявил проблему **M-06** в старом прямом dev-lifecycle из
`manage.sh`: PID-файл хранит только числовой PID, а `stop_component()` перед
`SIGTERM` и возможным `SIGKILL` не связывает PID с временем запуска и
исполняемым файлом. Если dev-процесс завершился, PID-файл остался, а PID был
переиспользован другим процессом того же пользователя, `manage.sh dev stop`
может завершить несвязанный процесс.

Этот lifecycle запускает бинарники непосредственно из `target/` через `nohup`,
ведёт `.run/pids` и `.run/logs`, а также пытается восстанавливать потерянные
PID-файлы поиском процессов. Он появился как удобство ранней разработки, но
больше не используется ни пользователем, ни текущим процессом разработки и
проверки OpenSwitcher.

Канонический пользовательский и проверочный путь теперь основан на собранном
Debian-пакете и `systemd --user`. Сборка и статические проверки выполняются через
`cargo`, а рискованные runtime-проверки — внутри согласованной ВМ-лаборатории.

## Решение

Не укреплять неиспользуемый PID-lifecycle дополнительным identity ledger или
pidfd-helper, а полностью вывести прямой dev-runtime из эксплуатации. Тем самым
устраняются не только конкретный stale PID, но и сама возможность, что
`manage.sh` самостоятельно выберет PID и отправит ему сигнал.

## Цели

1. Удалить из `manage.sh` самостоятельный запуск, учёт, поиск и остановку
   OpenSwitcher-процессов.
2. Гарантировать, что `manage.sh` больше не отправляет сигналы PID из
   пользовательских PID-файлов или process scan.
3. Сохранить каноническую сборку DEB, диагностику и управление через
   `systemd --user`.
4. Сохранить безопасную команду сборки локальных бинарников без их запуска.
5. Удалить внутренний dev-mode, который ослабляет managed lifecycle daemon и
   tray.
6. Закрыть M-06 архитектурным удалением опасной поверхности, а не новым слоем
   проверки вокруг неё.

## Не входит в задачу

- изменение runtime-поведения установленного Debian-пакета;
- изменение захвата устройств, input pipeline, коррекции текста, раскладок,
  clipboard или подобранных задержек;
- удаление команд `package`, `doctor` или управления через `systemd --user`;
- автоматическое удаление существующего каталога `.run` и старых логов;
- переработка `systemd` units или Debian maintainer scripts;
- добавление универсального process supervisor, identity ledger, pidfd-helper
  или `systemd-run`-обвязки;
- удаление явных диагностических переменных `OPEN_SWITCHER_*_DEBUG`.

## Командный интерфейс после изменения

### Сохраняется

- `./manage.sh build` — только собирает локальные бинарники;
- `./manage.sh package deb` — собирает канонический Debian-пакет;
- `./manage.sh doctor [linux-input|wayland]` — выполняет диагностику;
- `./manage.sh systemd install|start|stop|restart|status|logs|enable|disable` —
  управляет существующим безопасным systemd-путём;
- compatibility-команда `bootstrap linux-input`, которая уже является
  side-effect-free отказом с инструкцией по переходу на пакет.

Команда `build` остаётся верхнеуровневой, потому что она не создаёт фоновых
процессов и нужна перед `systemd install`. `OPEN_SWITCHER_PROFILE=debug|release`
продолжает выбирать каталог сборки для `build` и `systemd install`.

### Удаляется

- пространство имён `dev`, включая
  `dev build|start|stop|restart|status|logs|settings`;
- старые верхнеуровневые алиасы
  `start|stop|restart|status|logs|settings`;
- прямой запуск daemon, tray и settings из `target/`;
- автоматическое создание `.run/logs` и `.run/pids`;
- PID-файлы, process scan, `nohup`, ожидание по PID и прямые
  `SIGTERM`/`SIGKILL`.

Вызов `./manage.sh dev ...` завершается с ненулевым кодом и коротко сообщает,
что прямой dev-runtime удалён. Сообщение направляет:

- к `./manage.sh build` для сборки;
- к `./manage.sh package deb` для реальной установки и проверки;
- к `./manage.sh systemd ...` для уже существующего локального managed-пути.

Удалённые верхнеуровневые lifecycle-команды не перенаправляются автоматически
на systemd. Неявное изменение способа управления могло бы остановить или
запустить установленную пользовательскую службу вопреки намерению человека.
Они завершаются безопасным отказом и показывают актуальную справку.

## Удаление внутреннего dev-mode

`manage.sh dev start` выставляет `OPEN_SWITCHER_RUNTIME_MODE=dev`. В Rust-коде
эта переменная сейчас меняет не только диагностику:

- daemon не запускает tray watchdog;
- tray не пытается восстановить недоступный daemon и не завершает работу после
  неуспешного managed recovery.

После удаления единственного штатного производителя этой переменной внутренние
`RuntimeMode::Dev`, `is_dev_runtime_mode()` и соответствующие условные ветви
также удаляются. Daemon всегда запускает tray watchdog, а tray всегда использует
managed recovery policy.

Для установленного DEB это не является изменением поведения: без явного
`OPEN_SWITCHER_RUNTIME_MODE=dev` текущий код уже выбирает `Managed`. Удаляется
только скрытая возможность вручную ослабить lifecycle через переменную
окружения.

## Диагностические логи

Старый dev-launcher автоматически включал несколько подробных файловых логов в
`.run/logs`. Этот автоматизм удаляется вместе с launcher. Сами диагностические
возможности в Rust-коде сохраняются и по-прежнему могут быть явно включены
переменными `OPEN_SWITCHER_*_DEBUG` в контролируемом окружении, например в
ВМ-лаборатории или временном systemd override.

Обычный установленный DEB и сейчас не включает эти подробные логи по умолчанию,
поэтому пользовательская производительность и объём журналирования не меняются.

## Границы изменений

### `manage.sh`

- удалить `.run`, PID и dev-log state;
- удалить функции прямого process lifecycle;
- сохранить `build_binaries()` и сделать `build` явной поддерживаемой командой;
- оставить пути к `target/`, поскольку они нужны `build` и `systemd install`;
- обновить dispatch и `usage()` без неявного перенаправления старых lifecycle
  команд.

### `src/system/mod.rs`

- удалить `RUNTIME_MODE_ENV`, `RuntimeMode`, parser и тесты dev-mode;
- больше не предоставлять `is_dev_runtime_mode()`.

### `src/daemon/mod.rs`

- безусловно запускать существующий tray watchdog.

### `src/tray/dbus_listener.rs`

- безусловно использовать существующую managed recovery policy;
- удалить только dev-mode bypass, не менять retry count, задержки и реакцию на
  неуспешное восстановление.

### Документация

- обновить русскую и английскую README;
- убрать рекомендации прямого запуска из `target/`;
- описать `build`, package-first проверку и доступные systemd-команды;
- обновить remediation status и добавить русский validation report.

## Инварианты безопасности и совместимости

1. В `manage.sh` отсутствуют PID-файлы и прямые сигналы процессам.
2. `manage.sh` не ищет OpenSwitcher-процессы через `ps` или `/proc`.
3. Удалённая команда никогда не преобразуется в systemd-действие неявно.
4. `build`, `package deb` и `doctor` не получают новых системных побочных
   эффектов.
5. Установленный DEB продолжает использовать тот же managed lifecycle.
6. Watchdog/recovery, уже активные в package mode, остаются активными.
7. Явные debug-переменные сохраняются; их автоматическое включение исчезает.
8. Существующие `.run`-файлы становятся инертными и никогда больше не читаются.

## Проверки

### Shell regression

Новый безопасный тест проверяет:

- `./manage.sh dev ...` даёт понятный отказ без запуска процесса;
- удалённые верхнеуровневые lifecycle-команды не вызывают systemd и не
  запускают бинарники;
- `./manage.sh --help` показывает `build`, `package`, `doctor` и `systemd`, но
  не рекламирует dev-runtime;
- в `manage.sh` отсутствуют прежние PID/process-control функции и state paths;
- `bash -n manage.sh` проходит.

Первый красный тест строится на безопасном `dev help`/справочном пути и не
запускает текущие `start` или `stop`, чтобы тестирование старой реализации не
могло затронуть реальные процессы.

### Rust regression

- удалить тест parser-а `RuntimeMode::Dev`;
- существующие тесты watchdog, tray recovery и user-service controller должны
  пройти без изменения их managed-семантики;
- полный `cargo test --all-targets --all-features` подтверждает отсутствие
  регрессий.

### Package/systemd regression

- существующий `tests/manage_package_deb_test.sh` подтверждает, что локальный
  `systemd install/stop/restart` интерфейс сохранён;
- существующие package script tests проходят;
- каноническая сборка `./manage.sh package deb` завершается успешно;
- опасные runtime-тесты с физическим вводом для этой задачи не нужны: input
  pipeline и package runtime не меняются.

## Критерии готовности

M-06 считается закрытой, когда:

1. в репозитории нет поддерживаемого прямого dev-runtime;
2. `manage.sh` не хранит и не использует PID процессов;
3. Rust-код не содержит dev-mode bypass watchdog/recovery;
4. старые команды отказывают предсказуемо и не меняют состояние systemd;
5. shell, Rust и package regression gates проходят;
6. README и статус аудита отражают новый канонический workflow;
7. validation report явно фиксирует, что установленный DEB функционально не
   изменён.

## Рассмотренные альтернативы

### PID + start time + executable identity

Можно было хранить расширенный identity record и сверять его перед каждым
сигналом. Это сохранило бы recovery scan, потребовало бы миграции старых
PID-файлов, атомарной записи identity и тестового `/proc` seam, но всё равно
оставило бы небольшой check-then-signal race без pidfd.

### pidfd или `systemd-run --user`

pidfd устранил бы PID reuse на уровне ядра, а transient systemd units передали бы
lifecycle user manager. Оба подхода добавляют зависимости, compatibility policy
и новый код ради прямого режима, который больше не нужен.

### Выбранный retirement

Удаление имеет наименьшую сложность, полностью убирает опасную границу и
согласуется с package-first моделью проекта. Потеряно только неиспользуемое
удобство прямого запуска из дерева исходников.
